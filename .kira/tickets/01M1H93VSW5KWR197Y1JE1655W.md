The parent pointer was named `epic` because historically only an epic could be
a parent. With containers becoming a declared capability, any type can parent
others, so a field named after one type is wrong.

Decisions taken by the owner:

- On disk, new items write `parent:`; `epic:` is accepted on read **forever**.
  No migration command -- a file migrates the next time it is written.
- A file carrying BOTH keys is an error rather than silently preferring one.
- `--json` renames outright: `epic` -> `parent`, `epic_number` ->
  `parent_number`. No legacy duplicates, since kira is pre-1.0 and unpushed.
- The query keyword and the `--epic` CLI flag keep `epic` as an alias.

Verified against a repo whose file carries only the legacy key: `kira show`
displays the parent, `doctor` is clean, and a mutation rewrites it as
`parent: <ulid>` with the `epic:` line gone.

Deliberately unchanged: webui's `?epic=` URL query parameter and form field,
which are a web contract rather than a datamodel field. webui's templates DID
need updating where they read `datamodel.ListItem.Epic` -- Go templates are not
compile-checked, so that surfaced only as a 500 in the e2e dashboard test.
