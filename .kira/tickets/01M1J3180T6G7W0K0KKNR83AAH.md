`Store.Find` (`internal/core/find.go:106`) branches on `rgx.Installed()` into
two independent implementations, and they do not agree. The same command
against the same store returns different output depending on a binary the user
may not know is involved.

Verified by reading both paths:

- **`-C` context is silently dropped.** `findRipgrep` emits `RowContext` rows;
  `findFallback` never reads `args.Context` at all. So `kira find -C1` prints
  context with ripgrep installed and no context without it, with no warning
  that the flag did nothing.
- **Result order differs.** Only `NewFindResult` (the `--json` path,
  `find.go:34`) sorts. The human renderer prints whatever the backend produced,
  so the ripgrep path comes out unsorted and the fallback sorted.
- **Regex dialect differs.** ripgrep is Rust regex/PCRE2; the fallback is Go
  RE2. A pattern using a backreference or a lookaround works on one machine and
  fails on another.

A silent behavioural fork on an optional external dependency is the worst shape
this can take: it is invisible until two people compare output and disagree.

Options, roughly in order of honesty:

1. Drop the ripgrep path and always use the Go implementation. One behaviour
   everywhere; slower on very large stores, which for a Markdown ticket store
   is unlikely to matter.
2. Keep both but make them agree: sort in one place, implement `-C` in the
   fallback, and restrict the accepted pattern syntax to what RE2 supports.
3. Tell the user which backend ran, so a divergence is at least attributable.

Option 1 is the smallest and removes the fork rather than maintaining it.

Note a YAGNI audit has separately proposed removing `kira find` entirely, on
the grounds that it wraps ripgrep over plain Markdown files the user can grep
directly. If that is accepted this ticket disappears with it -- but the bug
should not be left standing on the assumption that removal will happen.
